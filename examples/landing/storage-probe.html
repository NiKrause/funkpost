Storage probeSpeicher-Probe

Two questions that decide whether the recovery page can offer more than one storage service, and whether a backup can still be fetched when a gateway will not answer: do Pinata and Lighthouse talk to a page at all (CORS, without a server of ours), and does anybody on IPFS hold a CID at an address a browser can dial?

Zwei Fragen, die entscheiden, ob die Recovery-Seite mehr als einen Speicherdienst anbieten kann und ob eine Sicherung auch dann erreichbar ist, wenn ein Gateway schweigt: Sprechen Pinata und Lighthouse überhaupt mit einer Seite (CORS, ohne Server von uns), und hält irgendwer im IPFS-Netz eine CID unter einer Adresse, die ein Browser wählen kann?

The CORS checks need no credentials: they are sent with a deliberately invalid key. A browser blocks a cross-origin request before it is answered, so an answer of any kind — even 401 — is the proof, and a blocked request is the refusal. A real upload is a separate step further down, with a key you paste yourself.

Die CORS-Prüfungen brauchen keine Zugangsdaten: Sie gehen mit einem absichtlich ungültigen Schlüssel hinaus. Ein Browser blockiert eine fremde Anfrage, bevor sie beantwortet wird — jede Antwort, auch 401, ist also der Beweis, und eine blockierte Anfrage ist die Absage. Ein echter Upload ist ein eigener Schritt weiter unten, mit einem Schlüssel, den nur du einfügst.

CORS is decided per origin. What this page measures counts for the address in the bar below, and a result from localhost says little about nikrause.github.io.

CORS gilt pro Herkunft. Was diese Seite misst, gilt für die Adresse unten, und ein Ergebnis von localhost sagt wenig über nikrause.github.io.

ObservationMeaning
A status came back — even 401 or 404CORS is fine for this origin: the browser let the answer through. The status is about the key or the CID, not about reachability.
TypeError: Failed to fetchThe browser blocked it. Either no CORS headers, or the host is unreachable from here — the two look identical to a page, which is why step 1 exists.
An upload endpoint is blocked, although a GET to the same host answersThe service allows the preflight and then forgets the header on its error answer. Measured on Pinata, 23 September 2026: the preflight says Allow-Origin: *, the 401 carries nothing. Only a real upload with a valid key decides whether success answers differently.
The same router answers, then is blocked minutes laterNot your network: delegated-ipfs.dev sends the CORS header only sometimes on /providers. Measure more than once, and ask the second router too.
Step 1 blocked as wellThe network or this browser is the cause, not the vendor. Nothing else on this page means anything until it passes.
Providers found, 0 browser-dialableThe bytes are on IPFS but only behind TCP or QUIC. A page cannot fetch them directly, so a gateway stays the only way in.
Providers found, some wss, webtransport or webrtc-directA browser could dial them and bitswap the blocks — the fallback in funkpost#127 is possible for this CID.
No providers at allNobody announced it, or the router does not know yet. For a fresh upload, retry in a few minutes before concluding anything.
